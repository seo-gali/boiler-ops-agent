# 프로젝트 구조 점검과 확장 설계

2026-11-11에 점검을 시작했고 2026-11-15에 문서 정리와 아래 코드 개선을 적용했다. 이 앱은 과거 CSV를 Kafka로 재생하고 API·WebSocket을 거쳐 브라우저에 표시한다. AI는 읽기 전용 근거를 조회하고, 별도 승인 연습은 SQLite의 가상 값만 바꾼다. GitHub Pages에는 소개 문서만 제공한다.

평가 전제는 README의 로컬 실행, API 프로세스 1개, CSV 1개, 소수의 동시 사용자다. 이 범위에서 구조를 전면 교체할 근거는 찾지 못했다. 수평 확장·여러 설비군·장기 AI 작업을 지원하려면 프로세스별 상태와 테스트의 구현 결합부터 바꿔야 한다. 앱 생성·공통 모델 통신·검사 개선은 적용했다. 여러 설비군·장기 AI 작업·공유 서버에 관한 B~D 확장안은 미구현 제안이며, 이번 개선으로 서버 간 상태가 공유되지는 않는다.

## 2. 적용한 개선과 남은 항목

후속 구현에서 두 앱이 같은 관측을 반환하는 실패를 재현한 뒤 수정했다. 아래 1~6은 코드·검사·의존성 선언에 반영했다. 검증 범위는 10절에 구분했다.

### 1. HTTP·WebSocket을 요청 앱의 상태에 연결

[main.py](../backend/app/main.py)에 `create_app()`을 추가했다. HTTP는 `request.app`·`http.app`, WebSocket은 `ws.app`의 자원을 사용한다. 앱마다 HTTP 지표와 CSV 동시 한도를 만들고 기존 Uvicorn `backend.app.main:app` 실행 경로는 유지한다.

기존에는 서로 다른 관측을 가진 앱 두 개에 요청해도 모두 첫 번째 앱의 관측을 반환했다. [API 검사](../scripts/check-api-performance.py)에서 HTTP·WebSocket 관측, 연결 정리, 세션 회수, CSV 포화와 지표가 앱 간에 섞이지 않는지 확인한다. [신뢰성 검사](../scripts/check-operational-reliability.py)도 자체 앱을 생성한다.

### 2. 모델 통신을 공통 모듈로 이동

[공통 통신](../backend/app/model_client.py)으로 `model_json`, 모델 옵션과 리다이렉트 차단을 옮겼다. [AI 서비스](../backend/app/agent/service.py)와 [Simulator](../backend/app/simulator/service.py)가 이 모듈을 사용하므로 Simulator가 AI 조회 서비스를 가져오지 않는다. 계획·근거·답변과 승인 정책은 각 기능에 남겼다.

격리 검사로 JSON 계약, 180초 제한, 외부 주소·리다이렉트 차단과 응답 크기 제한을 확인한다. 실제 모델·주소·인증 환경은 변경하지 않았으며 공급자 플러그인이나 새 설정도 추가하지 않았다.

### 3. 브라우저 검사에서 React 내부·청크명 의존 제거

[번들 검사](../scripts/check-bundle-performance.mjs)의 사설 DevTools/Fiber 계측·생성 파일명 검사와 [공장 화면](../frontend/src/BoilerScene.tsx)의 계측용 `SceneCanvas.displayName`을 삭제했다. 초기 전송량·청크 크기·사용하지 않는 화면의 API 요청·선택·카메라·초안·WebGL 대체 검사는 유지한다.

관측 10개 후 보이는 센서 값과 Canvas 동일성을 검사한다. 구독 갱신은 기존 공개 Profiler 검사에서 따로 확인한다. 사설 계측을 제거했으므로 이번 검사에서 SceneCanvas 재렌더 0회를 측정했다고 주장하지 않는다.

### 4. SQL 검사에서 실제 초기화 경로와 응답 계약 사용

[API 검사](../scripts/check-api-performance.py)의 `sql_queries()`는 실제 Simulator 생성자로 새 임시 DB를 만든다. 수동 스키마 복제·생성자 우회·정확한 SQL 횟수·인덱스 이름 검사를 제거했다.

1행·20행에서 조회 수가 비례해 늘지 않는지 비교하고 다른 소유자 제외·정렬·커서·페이지 크기를 결과로 검사한다. 더 적은 SQL도 통과한다. 기존 DB·스키마·데이터는 변경하지 않았으며 이번 검사에서 만든 임시 자원만 사용한다.

### 5. 모델 계산 검사와 공통 예측 E2E 분리

[통합 E2E](../scripts/e2e.mjs)에서 특정 예측식과 7,000개 초과 표본 가정을 제거했다. 입력·선택 모델·유한 예측값·예측 시각·평가 자료·데이터 출처와 화면/API/도구의 일치를 확인한다. [고정 질문 모델 평가](../scripts/review-agent.mjs)는 그 목적대로 유지한다.

두 기존 모델의 계산식과 학습 경계는 [격리 검사](../scripts/check-api-performance.py)의 임시 모델 산출물로 확인한다. Naive·선형 모델 각각 실제 예측 HTTP·읽기 도구까지 연결해 대조한다. 수정한 전체 연결 E2E는 이번에 실행하지 않았으므로 그 스크립트의 새 통과를 주장하지 않는다.

### 6. 직접 사용하는 Python 패키지의 선언 정리

- **대상:** [pyproject.toml](../pyproject.toml), `uv.lock`, Pydantic·Starlette 직접 사용 코드.
- **이전 문제:** 스키마와 HTTP 응답·비동기 실행을 직접 사용하지만 두 패키지가 간접 의존성으로만 선언돼 있었다.
- **변경:** `pydantic>=2,<3`, `starlette<2`를 직접 선언하고 lock의 프로젝트 의존성·요구사항 메타데이터를 갱신했다. 패키지 설치·업그레이드는 하지 않았다.
- **검증:** lock의 24개 패키지와 버전이 변경 전과 모두 일치하며, 설치된 Pydantic 2.13.5·Starlette 1.7.0도 유지된다. 오프라인 lock 정합성 검사가 통과했다.

| 선언 | 확인한 사용처 | 판단 |

| FastAPI | HTTP·WebSocket·입력 검증·예외 | 유지 |

| React·react-dom | 화면·루트·상태·구독 | 유지 |

## 4. 문서 맵과 레거시 정리

[문서 맵](README.md)을 추가해 기능별 현행 지침, 실행 안내, 설계 제안, 과거 결과와 생성 파일의 책임을 연결했다. 프로젝트 계획의 중복 Phase 링크 표는 문서 맵 링크로 대체했다. 이 문서는 현재 진단과 앞으로의 제안을 담당하며 기능 요구사항을 대신하지 않는다.

이전 공장 화면·선택 화면 결과의 `현재` 상태 표현을 당시 날짜로 바꾸고 현행 지침으로 연결했다. 여러 날짜가 있는 작업 화면 결과와 과거 성능 결과에도 후속 변경 위치를 명시했다. 특히 10월 성능 결과의 캐시·React 메모화 설명을 11월 3일 이후의 구현 지침으로 읽지 않게 했다. 최초 보안 감사는 이미 수정 전 기록으로 표시돼 있어 보완 결과와 함께 유지한다.

삭제한 파일·패키지는 없다. 삭제한 중복은 계획 문서의 기능별 링크 목록과 과거 결과의 현행 상태 표현이다. 초기 Phase 문서는 아직 유효한 기능 기준을 담고 있으므로 번호가 오래됐다는 이유로 제거하지 않았다. 검증 기록·화면·원본 출처도 보존했다.

## 5. 확장 목표와 변경 순서

목표는 기능별 책임을 나눈 단일 애플리케이션을 먼저 정리하고, 데이터량·동시 작업·배포 단위가 실제로 달라지는 경계만 분리하는 것이다. 다음 단계의 저장소·작업자·상태 공유는 해당 기능 요청과 측정 후 구현한다.

### 목표 책임

| 기능 경계 | 소유할 데이터·동작 | 확장 시 경계 |
| --- | --- | --- |
| 관측 수집 | 원본 검증, 실행 ID, 순서, 센서 품질 | 입력 어댑터 → 검증된 관측 → 현재 상태·이력 |
| 센서 목록 | 원본 Tag, 단위 근거, 설비 관계, 목록 버전 | 여러 데이터셋에서 같은 Tag가 충돌하지 않는 식별자 |

| HTTP·화면 | 인증된 요청·응답·실시간 전달·초안 | 상태를 직접 소유하지 않는 전달 계층 |

### A. 적용 완료: 한 프로세스에서 경계 만들기

앱 생성 함수·요청 앱 상태·공통 모델 통신과 테스트 분리를 반영했다. 서로 다른 관측·세션을 가진 앱 두 개를 HTTP·WebSocket으로 검증하며 테스트가 기본 전역 앱을 덮어쓰지 않는다. 기존 화면 패널·관측 저장소·Uvicorn 진입점은 유지한다.

폴더 전면 재배치, 기능별 기반 클래스, 공급자 플러그인은 추가하지 않았다. 다음 B~D는 요구사항과 측정 결과에 따라 적용할 확장안이다.

### B. 여러 데이터셋·큰 기간 조회: 식별자와 이력 저장 분리

현재 `Settings.dataset`, `BoilerState.current`, Simulator의 단일 `state(id=1)`은 각각 하나의 세계를 전제로 한다. 여러 설비군을 지원할 때 `source_id`와 목록 버전을 먼저 정의하고, 동일한 원본 Tag도 출처별로 구분한다. 관측·Trace·예측·제안이 같은 출처·run·목록 버전을 가리키게 한다. 다른 출처의 Trace를 승인 근거로 쓰지 못하게 한다.

기간 조회는 실제 CSV 길이·센서 수·동시 요청별 지연과 메모리를 측정한다. 현재 2개 동시 한도에서 429가 반복되고 목표 응답 시간을 넘으면 수집 시 이력 색인을 만들고 조회 경로를 분리한다. 저장 방식은 그 측정에 맞춰 고른다. 원본 문자열·행·품질·시간대와 파일 지문을 함께 보관하며 재생의 `source_row`와 기간 응답의 헤더 포함 행 번호를 혼동하지 않게 계약을 명시한다.

현재 두 종류 예측식의 키도 모델 산출물 버전으로 명시한다. 모델 대상·데이터 지문·학습/검증 경계를 확인하고, 이전 산출물의 읽기 호환성과 새 모델 평가를 따로 검증한다. 이 단계에서 두 번째 이력 구현이 생길 때만 필요한 조회 인터페이스를 둔다.

### C. 장기 AI 작업: 요청 수명과 작업 수명 분리

현재는 모델 두 번 호출에 브라우저가 최대 390초 기다린다. 취소하면 브라우저 대기만 끝나고 `Security.model_work()`의 작업은 계속될 수 있다. 동시 모델 작업은 프로세스당 2개다. 작업 재접속·완료 결과 회수 요구나 대기시간 문제가 확인되면 먼저 소유자가 있는 작업 ID와 상태 조회를 추가한다.

작업 상태는 대기·실행·성공·실패·만료로 구분하고, 고정한 관측 문맥·Trace ID를 저장한다. 이후에만 AI 작업자를 별도 프로세스로 옮기며 전역 동시 한도와 제한된 대기열을 적용한다. 중복 작업 방지 키는 AI 요청에 적용하고 사람의 승인 확인을 재사용하는 수단으로 쓰지 않는다. 처리 지연·사용자 취소·작업자 재시작 후 결과 소유권을 검사한다.

### D. 공유 서비스: 읽기 모델·인증·쓰기를 정리한 뒤 서버 늘리기

현재 상태에서 Uvicorn worker 수만 늘리면 로그인한 프로세스와 다음 요청의 프로세스가 달라 401이 발생할 수 있다. 각 프로세스가 독립 Kafka 그룹으로 과거 기록부터 읽으므로 관측·최근 이력도 서로 달라질 수 있고 CSV·모델 한도도 합산되지 않는다. 이는 현재 단일 프로세스 계약의 확장 한계다.

공유 배포의 목표 흐름은 다음과 같다.

```text
원본/입력 → Kafka → 관측 처리자 → 출처별 현재 상태·이력 저장
                                   ↓
브라우저 ↔ API·실시간 전달 서버 ↔ 관측 조회
                ├─ 소유자별 AI 작업 → AI 작업자 → Trace·결과
                └─ 승인 서비스 → 제안·상태·Audit 저장
```

API는 공통 관측 버전과 공유 세션·권한을 읽는다. 한 출처의 관측 순서를 유지하며 최신 스냅샷과 이후 이벤트의 연결 기준을 정한다. 재연결 시 누락을 숨기지 않는다. 승인 데이터는 공유 트랜잭션 저장소에서 revision·소유권·출처·근거 재사용을 한 번에 검사한다. SQLite를 교체하더라도 이 트랜잭션을 이벤트 여러 개로 먼저 쪼개지 않는다.

공유 세션 저장, 관계형 저장소 전환과 작업 전달 방식은 별도 선택 사항이다. Redis·새 메시지 브로커·Kubernetes·마이크로서비스를 일괄 도입할 근거는 없다. API 두 인스턴스 간 로그인·로그아웃, 같은 출처의 관측 일치, 중복 승인 1회 실행, 장애 후 결과 회수와 백업 복구가 검증된 뒤 트래픽을 분산한다. 스키마·데이터·패키지·배포 변경은 해당 승인 범위에서 별도 진행한다.

| 검사 종류 | 유지할 계약 | 분리할 구현 가정 |

기존 검사를 일괄 삭제하거나 전부 단위 테스트로 바꾸지 않는다. 사용자 계약을 보존하는 검사부터 남기고, 구현 특성 검사는 별도 성능 진단으로 구분한다. 공통 테스트 도구를 만들기 전에는 앱 생성 경계와 실제 자원 초기화를 우선한다.

## 7. 현재 운영 기술의 판단

| 상황과 방법 | 이 프로젝트에서의 판단 |
| --- | --- |
| 반복 조회가 느림 → 데이터 처리량 줄이기 | 조회 결과를 보관하지 않는다. 요청마다 CSV의 선택한 열을 한 번 읽고, 행별 전체 센서 사전 생성을 없앤다. 반복 조회도 파일 읽기 비용이 들며 실제 읽기 시간과 메모리를 측정한다. |
| 쓰기 요청이 몰림 → 대기열(큐) | 센서 데이터는 이미 Kafka가 전달한다. 승인 연습은 결과를 즉시 확인하는 짧은 저장 작업이다. 지금은 별도 대기열이 필요하다는 측정 근거가 없다. |
| 접속자가 많음 → 여러 서버로 요청 분산 | 현재는 API 서버 하나를 사용한다. 서버를 늘리려면 로그인 상태·요청 한도·관측값을 함께 쓰는 방법부터 정해야 한다. 요청을 나누는 장치인 로드 밸런서만 추가하면 해결되지 않는다. |
| DB 읽기가 많음 → 읽기용 복사본 | 화면 값은 메모리에서, 기간 데이터는 CSV에서 읽는다. DB 복사본을 만들어도 CSV 조회는 빨라지지 않는다. |
| DB 쓰기가 많음 → 데이터를 여러 DB로 나누기(샤딩) | DB에는 연습용 상태·변경안·기록만 저장하며 보관 한도가 있다. 나눠 저장해야 할 만큼의 쓰기량은 확인하지 않았다. |
| DB 조회가 느림 → 빠른 검색을 위한 인덱스 | 사용자별 제안과 기록을 찾는 인덱스가 이미 있다. 확인한 경로는 상태 조회 2회, 기록 조회 1회다. 행마다 추가 조회를 반복하는 N+1 문제는 이 경로에서 발견하지 않았다. |
| 파일 전송이 느림 → 외부 파일 저장소·CDN | 현재 앱은 로컬에서 실행하고 소개 문서만 정적으로 제공한다. 공유 배포에서 느려지면 파일 크기·압축·캐시 설정부터 확인한다. 원본 CSV를 공개 CDN으로 옮기지 않는다. |
| 연결이 잠깐 끊김 → 간격을 두고 재시도 | WebSocket은 재시도 간격을 1초부터 최대 10초까지 늘린다. Kafka 수신은 1초 간격으로 다시 시도한다. 승인 요청은 중복 실행을 피하기 위해 자동 반복하지 않는다. |
| 요청이 너무 많음 → 요청 수·동시 작업 제한 | 로그인·사용자·모델·WebSocket 한도가 있다. CSV 읽기는 API 서버 하나에서 동시에 2개까지만 허용하고, 브라우저도 센서를 하나씩 조회한다. |
| 외부 서비스가 계속 실패함 → 호출을 잠시 멈추기(서킷 브레이커) | Ollama 호출은 동시에 2개까지 허용하고 시간 제한을 둔다. 반복 장애가 다른 요청까지 막는지 확인한 뒤 추가 차단이 필요한지 판단한다. |
| 같은 요청을 다시 보냄 → 중복 처리 방지 식별자(멱등성 키) | 이미 승인한 제안이나 오래된 변경 횟수로는 다시 실행할 수 없다. 응답이 끊기면 서버 결과를 읽는다. 같은 요청에 같은 응답을 돌려주는 일반적인 멱등성 키 기능은 아직 없다. |
| 실패 원인을 찾기 어려움 → 요청별 기록·처리 지표 | HTTP 요청마다 식별자를 붙이고 요청 경로·결과 상태·걸린 시간을 남긴다. 운영자는 `/api/metrics/http`에서 요청·오류 수와 평균·최대 시간을 볼 수 있다. |

## 8. 기존 보완과 운영 한계

아래는 이번에 새로 구현한 기능이 아니라 기존 코드와 이전 결과에서 확인한 상태다.

승인 응답이 끊겨도 서버에서 실행 결과를 다시 확인한다. 결과가 불명확하면 추가 결정을 막고 사용자가 다시 확인할 수 있게 했다. 쓰기 요청을 자동 반복하지 않는다.

CSV 조회는 브라우저에서 하나씩 보내고 서버에서는 동시에 2개까지만 읽는다. 요청이 더 들어오면 기다리게 쌓아 두는 대신 429 상태와 재시도 안내를 보낸다. 실제 사용자 수가 늘었을 때의 처리 시간은 아직 측정하지 않았다.

조회 결과 캐시를 제거하고 CSV를 읽는 과정에서 불필요한 전체 센서 사전을 만들지 않게 했다. Kafka 배치 읽기와 토픽 확인은 함께 시작한다. 예측·도구·근거 파일 조회는 API의 다른 요청을 막지 않도록 기존 실행기로 넘긴다. [데이터 처리·비동기 검사 결과](results/phase7-data-oriented.md)에 바뀐 경로와 측정 범위를 정리했다.

HTTP 요청에는 식별자와 처리 시간을 기록한다. 비밀값이나 질문 전체를 로그에 넣지 않는다. 지표는 서버를 다시 시작하면 초기화되며, 여러 서버를 합친 수치나 상위 몇 % 요청의 처리 시간은 제공하지 않는다.

다음 DB 구조 변경 전에는 별도 테스트 환경에서 백업·변경 적용·복구를 확인해야 한다. [기존 신뢰성 보완 검증](results/phase7-operational-reliability.md)은 오류를 의도적으로 발생시킨 API·브라우저 검사다. 실제 운영 부하 시험이나 전체 보안 점검을 마쳤다는 뜻은 아니다.

문서 원본과 소스 미리보기는 생성·정적 링크·브라우저 검사를 거쳐 함께 갱신한다. 브라우저는 Playwright에 기본 Chromium 실행 파일이 없어 기존 Chrome `157.0.8103.78`을 실행 시 지정한다. 패키지·브라우저 설치와 테스트 소스의 실행 경로 변경은 하지 않았다. API 결과는 `artifacts/repo-review/implementation-*.json`, 화면 결과는 `artifacts/e2e/operational-reliability/result.json`에 남긴다.

읽은 범위는 진입점·설정·의존성·주요 데이터/AI/승인 경로·관련 화면과 검사·문서다. 모든 CSS 규칙과 센서 정의 118개를 항목별로 재감사하지 않았다. 실제 CSV·Kafka·Ollama 전체 연결 E2E, 최신 취약점 조회, 운영 부하·백업 복구·실제 보조기기는 미검증이다. 비밀 파일·기존 DB·설치된 패키지·배포는 변경하지 않았다. lock은 프로젝트의 직접 의존성 메타데이터만 갱신했다.
