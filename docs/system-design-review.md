# 현재 규모의 시스템 설계 판단

2026-11-02 코드 기준이다. 현재 앱은 공개 CSV → Replay Producer → 단일 partition Kafka → FastAPI 메모리 관측 상태 → WebSocket → React이며, 승인 연습만 로컬 SQLite를 사용한다. 세션과 요청 한도는 단일 API 프로세스의 메모리에 있다. GitHub Pages는 설명 문서를 제공한다.

아래 항목은 증상에 대한 후보이며 전부 추가해야 하는 체크리스트가 아니다. 실제 사용자 수·요청 지연·오류율·디스크와 CPU 사용을 측정한 뒤 해당 병목에만 적용한다.

| 제안 | 현재 구현과 판단 |
| --- | --- |
| 느린 읽기 → 캐시 | 기간 조회 성공 결과를 최대 16개 캐시하고 파일 수정 시각·크기 등으로 구분한다. 첫 조회와 여러 센서 동시 조회는 CSV를 각각 순회하므로 이 부하부터 측정한다. Redis를 즉시 추가할 근거는 없다. |
| 쓰기 급증 → 큐 | 관측 이벤트는 이미 Kafka로 분리한다. 승인 연습은 짧은 SQLite 트랜잭션이며 즉시 결과·revision을 확인한다. 측정 없이 승인 작업까지 비동기 큐로 바꾸면 진행 상태·중복 처리·취소 계약을 추가해야 한다. |
| 트래픽 과다 → 로드 밸런서 | 현재 단일 프로세스 운영 범위다. 먼저 세션·한도·관측 상태를 여러 프로세스에서 어떻게 공유할지 정해야 한다. LB만 붙이면 사용자 세션이 요청마다 달라질 수 있다. |
| 읽기 중심 DB → 읽기 복제본 | 화면의 관측값은 메모리, 기간 데이터는 CSV다. SQLite 읽기를 복제해도 CSV 병목은 해결되지 않는다. 현재는 불필요하다. |
| 쓰기 중심 DB → 샤딩 | 현재 DB는 연습용 상태·제안·Audit이며 보존 한도도 있다. 샤딩이 필요한 쓰기량은 측정하지 않았다. 트랜잭션·소유권·revision을 여러 DB에 나누는 비용이 더 크다. |
| 느린 쿼리 → 인덱스 | 이미 audit(owner,id), proposals(owner) 인덱스를 사용한다. 확인한 경로는 상태 2 SELECT·Audit 1 SELECT로 N+1이 없다. 새 인덱스는 느린 실제 SQL과 실행 계획에 근거해 추가한다. |
| 느린 파일 → 오브젝트 스토리지·CDN | 현재 로컬 앱과 정적 설명 페이지를 제공한다. 원본 CSV를 공개 CDN으로 옮기지 않는다. 공유 배포에서 정적 파일의 네트워크 지연이 확인되면 캐시 정책·압축·용량을 먼저 확인한다. |
| 일시적 장애 → 백오프 재시도 | WebSocket은 1초부터 최대 10초의 지수 백오프, Kafka 소비자는 1초 간격 재시도가 있다. 쓰기 요청을 자동 재시도하기 전에 실제 실행 결과 확인이 필요하다. 재시도 횟수·대상·종료 조건을 구분한다. |
| 요청 과다 → 속도 제한 | IP·로그인·사용자·모델·WS 한도에 더해 CSV 메타데이터·기간 조회는 프로세스 동시 2개로 제한한다. 브라우저는 센서별 조회를 순차 실행한다. 여러 worker에서 한도가 공유되지 않는 제약은 유지한다. |
| 서비스 장애 → 서킷 브레이커 | 로컬 Ollama 호출은 동시 2개와 시간 제한으로 경계를 둔다. 모델의 반복 장애로 정상 요청이 지속적으로 막히는 현상이 측정되면 빠른 실패·복구 확인을 검토한다. 현재 분산 서킷 브레이커를 추가할 근거는 없다. |
| 중복 요청 → 멱등성 키 | 승인에는 status·revision 검사, 제안에는 단일 사용 근거 제약이 있다. 응답 유실·오류 시 GET으로 실제 결과를 확인하며 POST를 자동 재전송하지 않는다. 일반적인 멱등성 키와 동일 응답 재전달 기능을 도입한 것은 아니다. |
| 장애가 안 보임 → 로그·메트릭·트레이싱 | 모든 HTTP 요청의 서버 생성 ID·경로별 상태·지연을 기록한다. operator는 `/api/metrics/http`에서 요청·오류 수와 평균/최대 시간을 읽는다. 단일 프로세스 지표이며 분산 추적이나 percentile 측정은 아니다. |

## 보완 결과와 남은 작업

1. 승인 응답 유실 뒤 결과 재확인과 미확인 상태의 명시적 재조회·재확인을 구현했다.
2. 브라우저 CSV 조회를 순차 처리하고 서버 메타데이터·기간 조회에 공유 동시 2개 한도를 적용했다. 운영 부하별 지연 측정은 남아 있다.
3. HTTP 요청 ID, 경로·상태·처리 시간 로그와 운영자용 오류·지연 지표를 구현했다. 비밀값·질문 원문 전체를 로그에 넣지 않는다.
4. 다음 DB 스키마 변경 전에 백업·적용·복구를 격리 환경에서 검증한다.

영상 제작 후 사용자의 추가 요청으로 위 1~3번을 최소 범위에서 보완했다. DB 스키마·운영 데이터·의존성·분산 구조는 바꾸지 않았다. [검증 기록](results/phase7-operational-reliability.md)은 격리된 요청·브라우저 검사이며 운영 부하 시험·취약점 점검·침투 검사를 대신하지 않는다.

## 근거와 알려진 불일치

- [보안 경계](../backend/app/security.py): 메모리 세션·속도·모델/WS 한도.
- [기간 조회](../backend/app/domain/history.py), [다중 센서 요청](../frontend/src/OperationsAnalysis.tsx): 파일 기반 캐시와 센서별 순차 요청.
- [Simulator](../backend/app/simulator/service.py), [화면](../frontend/src/SimulatorPanel.tsx): 트랜잭션·revision·소유권과 응답 유실 뒤 서버 결과 재확인.
- [HTTP 관측](../backend/app/observability.py): 요청 ID, 안전한 내부 오류, JSON 로그와 경로별 집계.
- [실시간 재연결](../frontend/src/telemetry.ts), [Kafka 소비](../backend/app/streaming/consumer.py): 백오프·재시도와 수신 상태.
- [실행 범위](local-development.md): 단일 API 프로세스 운영.

기존 보안 지침과 달랐던 일반 DB 오류의 공개 코드 처리는 HTTP 관측 경계에서 `internal_error`·요청 ID를 반환하도록 보완했다. 실제 Simulator 라우트에 SQLite 오류를 주입해 내부 원문이 노출되지 않는 것을 확인했다.
