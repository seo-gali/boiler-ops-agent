# 현재 규모의 시스템 설계 판단

2026-11-03에 확인한 코드 기준이다. 이 앱은 내 컴퓨터에서 과거 CSV를 재생하고, Kafka와 API 서버를 거쳐 브라우저에 값을 보여준다. 승인 연습의 상태와 결과는 SQLite에 저장한다. 로그인 상태와 요청 한도는 실행 중인 API 서버의 메모리에 둔다. GitHub Pages에서는 앱 소개 문서만 제공한다.

지금은 서버를 여러 대로 늘리는 것보다 어떤 요청이 느리거나 실패하는지 먼저 확인하는 편이 낫다. 아래 기술은 모두 설치해야 하는 목록이 아니다. 실제 사용자 수, 처리 시간, 오류 수와 컴퓨터 사용량을 보고 필요한 항목만 고른다.

## 제안별 판단

| 상황과 방법 | 이 프로젝트에서의 판단 |
| --- | --- |
| 반복 조회가 느림 → 데이터 처리량 줄이기 | 조회 결과를 보관하지 않는다. 요청마다 CSV의 선택한 열을 한 번 읽고, 행별 전체 센서 사전 생성을 없앤다. 반복 조회도 파일 읽기 비용이 들며 실제 읽기 시간과 메모리를 측정한다. |
| 쓰기 요청이 몰림 → 대기열(큐) | 센서 데이터는 이미 Kafka가 전달한다. 승인 연습은 결과를 즉시 확인하는 짧은 저장 작업이다. 지금은 별도 대기열이 필요하다는 측정 근거가 없다. |
| 접속자가 많음 → 여러 서버로 요청 분산 | 현재는 API 서버 하나를 사용한다. 서버를 늘리려면 로그인 상태·요청 한도·관측값을 함께 쓰는 방법부터 정해야 한다. 요청을 나누는 장치인 로드 밸런서만 추가하면 해결되지 않는다. |
| DB 읽기가 많음 → 읽기용 복사본 | 화면 값은 메모리에서, 기간 데이터는 CSV에서 읽는다. DB 복사본을 만들어도 CSV 조회는 빨라지지 않는다. |
| DB 쓰기가 많음 → 데이터를 여러 DB로 나누기(샤딩) | DB에는 연습용 상태·변경안·기록만 저장하며 보관 한도가 있다. 나눠 저장해야 할 만큼의 쓰기량은 확인하지 않았다. |
| DB 조회가 느림 → 빠른 검색을 위한 인덱스 | 사용자별 제안과 기록을 찾는 인덱스가 이미 있다. 확인한 경로는 상태 조회 2회, 기록 조회 1회다. 행마다 추가 조회를 반복하는 N+1 문제는 이 경로에서 발견하지 않았다. |
| 파일 전송이 느림 → 외부 파일 저장소·CDN | 현재 앱은 로컬에서 실행하고 소개 문서만 정적으로 제공한다. 공유 배포에서 느려지면 파일 크기·압축·캐시 설정부터 확인한다. 원본 CSV를 공개 CDN으로 옮기지 않는다. |
| 연결이 잠깐 끊김 → 간격을 두고 재시도 | WebSocket은 재시도 간격을 1초부터 최대 10초까지 늘린다. Kafka 수신은 1초 간격으로 다시 시도한다. 승인 요청은 중복 실행을 피하기 위해 자동 반복하지 않는다. |
| 요청이 너무 많음 → 요청 수·동시 작업 제한 | 로그인·사용자·모델·WebSocket 한도가 있다. CSV 읽기는 API 서버 하나에서 동시에 2개까지만 허용하고, 브라우저도 센서를 하나씩 조회한다. |
| 외부 서비스가 계속 실패함 → 호출을 잠시 멈추기(서킷 브레이커) | Ollama 호출은 동시에 2개까지 허용하고 시간 제한을 둔다. 반복 장애가 다른 요청까지 막는지 확인한 뒤 추가 차단이 필요한지 판단한다. |
| 같은 요청을 다시 보냄 → 중복 처리 방지 식별자(멱등성 키) | 이미 승인한 제안이나 오래된 변경 횟수로는 다시 실행할 수 없다. 응답이 끊기면 서버 결과를 읽는다. 같은 요청에 같은 응답을 돌려주는 일반적인 멱등성 키 기능은 아직 없다. |
| 실패 원인을 찾기 어려움 → 요청별 기록·처리 지표 | HTTP 요청마다 식별자를 붙이고 요청 경로·결과 상태·걸린 시간을 남긴다. 운영자는 `/api/metrics/http`에서 요청·오류 수와 평균·최대 시간을 볼 수 있다. |

## 보완한 부분과 남은 확인

승인 응답이 끊겨도 서버에서 실행 결과를 다시 확인한다. 결과가 불명확하면 추가 결정을 막고 사용자가 다시 확인할 수 있게 했다. 쓰기 요청을 자동 반복하지 않는다.

CSV 조회는 브라우저에서 하나씩 보내고 서버에서는 동시에 2개까지만 읽는다. 요청이 더 들어오면 기다리게 쌓아 두는 대신 429 상태와 재시도 안내를 보낸다. 실제 사용자 수가 늘었을 때의 처리 시간은 아직 측정하지 않았다.

조회 결과 캐시를 제거하고 CSV를 읽는 과정에서 불필요한 전체 센서 사전을 만들지 않게 했다. Kafka 배치 읽기와 토픽 확인은 함께 시작한다. 예측·도구·근거 파일 조회는 API의 다른 요청을 막지 않도록 기존 실행기로 넘긴다. [데이터 처리·비동기 검사 결과](results/phase7-data-oriented.md)에 바뀐 경로와 측정 범위를 정리했다.

HTTP 요청에는 식별자와 처리 시간을 기록한다. 비밀값이나 질문 전체를 로그에 넣지 않는다. 지표는 서버를 다시 시작하면 초기화되며, 여러 서버를 합친 수치나 상위 몇 % 요청의 처리 시간은 제공하지 않는다.

다음 DB 구조 변경 전에는 별도 테스트 환경에서 백업·변경 적용·복구를 확인해야 한다. [이번 보완 검증](results/phase7-operational-reliability.md)은 오류를 의도적으로 발생시킨 API·브라우저 검사다. 실제 운영 부하 시험이나 전체 보안 점검을 마쳤다는 뜻은 아니다.
